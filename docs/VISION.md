# Vision

## Core thesis

Modern apps do not just fail in code.
They fail in flows:

- date pickers
- booking paths
- permissions
- mobile layouts
- payment handoffs
- notification expectations
- camera / speech / OCR paths

BugWitness exists to test those flows and capture evidence in a form humans can
actually use.

## Product direction

BugWitness should become a practical testing companion for:

- web apps
- mobile web apps
- local-first apps
- browser extensions
- device-connected workflows

The emphasis is not on abstract benchmark charts.
It is on:

- "what happened"
- "what did we expect"
- "what proof do we have"
- "how reproducible is it"

## Why now

There is a gap between:

- heavy CI automation
- casual manual QA

Especially on real devices.

BugWitness should fill that gap with a system that can:

- guide scenario execution
- capture screenshots, OCR, speech, traces, and endpoint responses
- compare runs
- summarize findings clearly

## Mobile-first edge

Phones and tablets are not only targets.
They can also be probes.

That matters because many bugs only show up on:

- real mobile browsers
- real permissions flows
- real network conditions
- real touch interactions

## Naming direction

The name emphasizes evidence, not just execution.
The product should feel like:

- a witness
- a recorder
- a finder of truth

not merely another generic test runner.
